# Example tour: swarm-sync

Two reading paths generated by `codelearner.onboard` over
[swarm-sync](https://github.com/keithalindsay/swarm-sync) -- 68 files, 1,095
symbols, 6,531 reference edges, of which 313 are resolved in-repo `calls` edges
between non-test symbols. Nothing here was written or ordered by a model; the
whole file is `render_markdown(build_reading_path(conn, ...))` with a one-line
title, reproduced verbatim. Regenerating it against an unchanged swarm-sync
produces byte-identical output -- the ordering is deterministic, which is what
makes checking this file into version control worth doing.

Regenerate with:

```python

from codelearner import db
from codelearner.ingest import index_repo
from codelearner.onboard import build_reading_path, render_markdown

conn, _ = index_repo(Path("/path/to/swarm-sync"), index_path=Path("/tmp/ss.db"))
print(render_markdown(build_reading_path(conn, limit=10)))
print(render_markdown(build_reading_path(conn, topic="worktree creation and cleanup", limit=10)))
```

## What to look at when judging these

The claim a reading path makes is narrow and checkable: **every call edge inside
the tour points backwards.** Each stop's "Prerequisites already covered" list only
ever names stops with a lower number, and each "Coming up, uses this" list only
ever names higher ones. That is the property `tests/test_onboard.py` asserts over
a layered fixture, and it is the property that makes the tour readable top to
bottom instead of requiring the forward references a ranked list forces on you.

### Honest notes on this particular output

- **swarm-sync's non-test call graph has no cycles at all** -- 305 symbols, 305
  strongly-connected components, none with more than one member. So the cycle
  handling in `onboard/path.py` is exercised by the synthetic fixtures in
  `tests/test_onboard.py`, not by this document. Saying so is better than implying
  the feature was validated here.
- **Tour 1 leans heavily on `worktree/git_ops.py`.** That is not a bug in the
  clustering -- `git_ops` genuinely holds the highest-PageRank symbols in the repo
  -- but a repo-wide tour seeded from centrality will always be a tour of the
  repo's *most-called* code, which is its plumbing. It tells you what the codebase
  is built out of, not what it is for. For "what is it for", give it a topic.
- **Tour 2, depth 3, puts `_cleanup_worktree` before `add_worktree`.** No edge
  connects them, so no ordering rule is violated, and module clustering broke the
  tie towards `agent/runner.py`. It still reads slightly backwards to a human
  (teardown before creation). Ordering symbols that have no dependency
  relationship is exactly where deterministic graph work runs out of information,
  and this is what that looks like.
- **Class stops show `GitOpsError(...)`** because the extractor records no
  signature for a class. The stop is still correctly placed and its docstring
  carries the meaning, but the code block is filler.
